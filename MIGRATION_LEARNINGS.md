# Migration learnings: Adobe Commerce Marketplace → Edge Delivery Services

Source: https://commercemarketplace.adobe.com/ (Magento 2 / Adobe Commerce storefront with Live Search).
Target: AEM Edge Delivery Services with Document Authoring and the Adobe Commerce boilerplate (drop-ins).
Status (2026-11-20): all 4,353 catalogued URLs are in scope. Every page is imported into the local workspace,
except the 37 pages that could not be analysed during scoping. Nothing has been uploaded to DA, previewed or
published.

This file is excluded from the served site by `*.md` in `.hlxignore`.

---

## 1. How the product and listing pages were imported

### The approach: thin shells, not copied content
Product data (titles, prices, galleries, descriptions, reviews) was **not** copied into documents. Each page is
a small shell. It holds the commerce block plus the configuration that block needs. The drop-ins load
everything else from the Commerce catalog when the page is viewed.

| Page type | Pages | Shell contents |
|-----------|-------|----------------|
| Product detail (PDP) | 4,228 | optional `notice` block (PCI notice, 587 pages) → `product-details` with `defaultSku` → Metadata (Title, Description, Image, `sku`) |
| Category listing (PLP) | 97 | `h1` category title → `product-list-page` with `urlPath` + `pageSize 36` → Metadata |

Example PDP shell:
```html
<div class="product-details"><div><div>defaultSku</div><div>mageants/module-simpleconfigurable</div></div></div>
```
Example PLP shell:
```html
<h1>ERP &amp; Accounting Extensions for Adobe Commerce</h1>
<div class="product-list-page">
  <div><div>urlPath</div><div>extensions/accounting-finance/erp-accounting</div></div>
  <div><div>pageSize</div><div>36</div></div>
</div>
```

### Where the values come from
- **SKU:** comes from the JSON-LD `Product.sku` on each source page, so it is never guessed from the URL. The
  fallbacks are `data-sku` attributes, then visible "SKU:" text. All 4,228 pages had a JSON-LD SKU.
  Marketplace SKUs look like `vendor/module-name`, which is the Composer package name, not the URL slug.
- **Category path:** the URL path without `.html`. For example, `/themes/styles/look/colorful.html` becomes
  `themes/styles/look/colorful`, which matches Magento's `url_path`.
- **PDP or PLP:** decided per page inside the import script. A JSON-LD Product or `og:type=product` means
  PDP; anything else is PLP. One script (`tools/importer/commerce-import.js`) handles both types.

### Pipeline
1. Scope the site (catalog) → templates `product-detail` and `product-listing`.
2. Run the commerce workflow on one representative URL per template. The steps are scrape, detect page type,
   route, run Pass 1 (standard blocks) and Pass 2 (commerce parts), merge, then write
   `migration-work/commerce-templates.json` and `commerce-import.js`.
3. Copy the catalog's saved page captures into `tools/importer/bd-snapshots/<host>/<path>.html.html`. The
   live site can't be imported directly (see section 3).
4. Bundle once, run a pilot (4 pages), inspect the output, then run the full list.
5. Check every output file. Each PDP needs a non-empty `defaultSku` and each PLP needs its `urlPath`. Record
   `imported_at` in `commerce-templates.json`.

### Results
- PDP: 4,227 of 4,228 pages on the first run. The one failure had an empty (0-byte) snapshot copy, while its
  catalog capture was fine. I re-copied it and it then imported.
- PLP: 97 of 97 pages.
- Throughput was about 23 pages per minute from snapshots, so the PDP run took roughly 3 hours. Start long
  runs in the background, and do other work meanwhile, such as the PLP decomposition.

## 2. Scoping learnings

- **Sitemap discovery worked:** 4,353 URLs from `sitemap.xml`, all in one locale. About 97% are product pages
  (4,228), so the migration is mostly a commerce problem. Spend scoping effort on the few non-product
  templates.
- **The site rate-limits page loads.** Analysis is slow, and many failures are timeouts, not real errors.
  When the user chose "keep analyzing all", this was worth it: retrying the timed-out pages recovered most of
  them (6 of 8).
- **Count failed pages, not failed attempts.** I first reported 43 analysis errors. That number counted
  retries, and the real figure was 21 pages: 12 genuine 404s, 7 timeouts and 1 false 404. Always derive
  unique URLs before reporting. Don't quote the summary's error totals as page counts either.
- **Stacked-layout pages fragment blocks.** Some product pages loaded in a stacked (mobile-like) layout, so
  the buy box was detected as loose pieces (breadcrumb, partner profile, facets). Fold those pieces back
  into the parent block (`product-buy-box`), not into new blocks.
- **Commerce UI shows up as "blocks" during scoping.** Breadcrumbs, filter facets, the buy box and the
  seller profile on product pages all appear as blocks. They are generated by the platform or the drop-ins:
  - the breadcrumb is auto-generated from the site hierarchy, with no authored block;
  - `filter-facet` is part of `product-list-page`;
  - buy-box pieces are part of `product-details`.

  The **seller page header** (`partner-profile`) is the exception. It is real authored content and stays a
  block.
- **Odd pages get their own template.** An empty security-test page
  (`/test-input-onclick-alert-…-svg-onload-alert-1`) was not merged into the product pages.
- **Write review decisions into `catalog/review-instructions.md`.** Catalog roll-ups can reset
  classifications (for example, `canonicalModel` lost its auto-blocked marker). With the rules saved there,
  re-runs keep the user's decisions.
- **The user preferred one question at a time** for review items, each with a recommended option.

## 3. Gotchas

### Source site and importer
- **The live pages can't be imported directly.** RequireJS on the Magento pages stops the importer's helper
  script from loading ("WebImporter not available"). Import from saved snapshots in
  `tools/importer/bd-snapshots/` instead. The same error also appears when a snapshot file is **empty**, so
  check sizes after copying (a search for 0-byte files under bd-snapshots should return nothing).
- **The site is bot-protected.** Use the Bright Data fallback for scrapes and single fetches. The catalog's
  `catalog/.pages/<slug>/page.html` captures are the best snapshot source, because they need no extra live
  requests.
- **`<script>` tags are removed before `transform` runs.** Read JSON-LD in `preprocess` and pass it on
  through `params`.
- **Strip `.html` before `sanitizePath`.** Otherwise output becomes `slug.html.plain.html` and the preview
  returns 404.
- **Don't re-bundle the import script while a bulk import is using that bundle.** To run a second import at
  the same time, copy the bundle under a new name (`commerce-import-plp.bundle.js`), which also keeps the
  reports separate.
- **Source links are absolute and end in `.html`.** Seller pages and homepage cards linked to other pages as
  `https://commercemarketplace.adobe.com/<page>.html` (263 links). Left as they were, these would send
  visitors back to the old site. `transformers/commercemarketplace-links.js` (afterTransform, in every
  template import) rewrites links to **migrated** pages as site-relative paths without `.html` (`/<page>`), and
  keeps the query string and #fragment.
  - It only rewrites targets listed in `transformers/migrated-paths.js`, which is generated from
    `page-templates.json` (minus test-page). Regenerate that list when templates change.
  - Pages that were not migrated (`/partners`, `/contact-us`, `/legal/terms/*`, PDFs under `/static`) still
    point at the old site.
  - Audit links site-wide after every import: count absolute source-host links, `.html` links, and targets
    that weren't imported.
  - In local preview, site-relative links return 404 because pages are served under `/content/`. They resolve
    on the real site.
- **Low completeness scores are expected for commerce shells.** The importer's text-completeness warnings
  (for example, 26.7%) mean nothing here, because the shells drop product text on purpose. Don't send these
  pages into the visual-critique fix loop.

### Product page model (decide this before importing product pages)
- **The boilerplate assumes catalog-driven product URLs.** `getProductLink()` in `scripts/commerce.js`
  links every product to `/products/<url-key>/<sku>`; product lists, recommendations, cart, orders and
  search all use it. Importing one document per product at the old root URLs (as done here) leaves all of
  those links returning 404.
- **Choose the model first:** a single `/products/default` template with folder mapping, redirects from the
  old URLs, and generated SEO metadata (`tools/pdp-metadata`), versus one document per product. See
  `PRODUCT_PAGES_PLAN.md`.
- **Check the SKU format.** Marketplace SKUs all contain `/`, which the boilerplate's `getSkuFromUrl()`
  can't read. Look products up by `url_key` instead (it is filterable in Catalog Service).
- **The catalog can hold more than the sitemap** (here 4,341 against 4,228, including delisted and test
  products). A template makes all of them reachable, so carry over the old site's visibility rules.

### Commerce detection
- **The page-type detector can miss obvious product pages.** It only reads the first ~200k characters of
  `cleaned.html`. Marketplace product pages are over 1 MB, and "Add to cart" sits beyond that point, so the
  page was classified as CONTENT (0.5). Check JSON-LD `@type: Product` yourself, and override to PDP if the
  user agrees.
- **The PLP signals were weak but correct** (PLP, 0.6: generic filters, sort, grid). Live Search markup uses
  `#instant-search-facets-container`, `#selected-filters-container`, `#products-grid`, `#sorter`,
  `#livesearch-limiter` and `.pages-items`.
- **Some PLP captures show "no results" plus popular-search suggestions.** That panel comes from Live Search
  and is not authored content, so leave it out.

### Commerce configuration
- **The site configuration has no Commerce public config,** so preview pages show "Invalid Site
  Configuration".
  - For local preview only, a `config.json` copied from `demo-config.json` sits at the repo root. It is
    listed in both `.gitignore` and `.hlxignore`, so it is never committed or served.
  - The demo catalog has no Marketplace SKUs or categories. The shells render the layout, breadcrumb and
    "no results", but no products.
  - For real data, an org admin must add the Commerce endpoint, environment and headers to the site
    configuration. `catalog_api_endpoint` in `commerce-templates.json` is still empty for this reason.
- **`getProductSku()` reads two places.** On DA preview it reads `defaultSku` from the block; elsewhere it
  reads the `sku` metadata. Write both.

### Edge Delivery project specifics (this repo)
- **Local preview serves pages under `/content/`** (aem up with `--html-folder content`). Code that fetches
  fragments needs a fallback. The header and footer fetch `/content/nav.plain.html` first, then
  `/nav.plain.html`. The breadcrumb strips `/content` on localhost.
- **The breadcrumb ended up inside the header.** The auto-breadcrumb in `buildAutoBlocks` was also injected
  into fragments (nav), which broke the header. It is now limited to `main === document.querySelector('main')`.
- **This repo's `aem.js` doesn't handle section metadata,** and `aem.js` must not be edited. A small
  `section-metadata` block applies the styles instead.
- **The importer drops empty icon `<span>`s.** Write `:icon-name:` tokens instead and let the blocks turn
  them into images.
- **When a section transformer writes no section metadata,** add it in a page-scoped correction. This
  happens on single-section pages such as `/service-unavailable`.

### Working environment
- **The command guard blocks some inline commands.** It rejected inline scripts containing `/g` regexes,
  `cd -`, or bare `"/"` strings. Write helper scripts to `/tmp/scope-scripts/*.js` and run those instead.
- **Lint tools (ESLint, stylelint) are not installed,** so only `node --check` syntax checks ran.

## 4. Checklist for the next commerce site

1. Scope the site from its sitemap. Expect timeouts on rate-limited stores, and retry timeouts separately.
2. In the scoping review, fold platform UI (breadcrumb, facets, buy-box pieces) into the commerce blocks or
   auto-blocks. Keep only truly authored content as blocks. Save each decision in `review-instructions.md`.
3. Migrate non-commerce templates first (homepage, seller pages, legal pages, errors), plus header, footer
   and design.
4. Commerce workflow, one representative URL per template:
   - confirm the page type against JSON-LD, not only the detector;
   - take SKUs from JSON-LD;
   - take category paths from the URL without `.html`.
5. Write one import script for PDP and PLP that branches on JSON-LD. Import from snapshots, run a pilot, then
   the full list in the background.
6. Check every output file for a SKU or `urlPath`, and check for empty snapshots. Retry the failures.
7. Tell the user plainly:
   - the site configuration needs Commerce settings from an org admin;
   - the preview shows no real products until then;
   - all changes are local until they ask for an upload or publish.
